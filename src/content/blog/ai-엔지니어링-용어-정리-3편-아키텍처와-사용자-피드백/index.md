> 『AI 엔지니어링』을 읽고 메모한 키워드를 다시 조사해 정리한 시리즈의 3편이자 마지막입니다.
> 1편: 파운데이션 모델과 평가 (1~4장) · 2편: 프롬프트, RAG, 에이전트 (5~6장) · **3편: 아키텍처와 사용자 피드백 (7~10장)**

---

## 들어가며

책의 뒷부분(7~9장)은 파인튜닝, 데이터셋 엔지니어링, 추론 최적화입니다. 읽으면서 메모가 눈에 띄게 줄었습니다. 모델을 직접 학습시키거나 서빙하지 않는 제 일과 거리가 있었기 때문입니다. 그래도 몇 개 용어는 API 사용자 입장에서도 자주 마주치기 때문에 1절에서 짧게 짚습니다.

메모가 다시 늘어난 곳은 10장입니다. 앞에서 배운 조각을 **하나의 시스템으로 조립하는 아키텍처**와, 만들고 난 뒤 **사용자 피드백을 어떻게 받아 다시 돌리는지**. 둘 다 프론트엔드 개발자가 직접 손대는 층입니다.

---

## 1. 7~9장에서 알아두면 좋은 용어

깊이 들어가지 않고 "이 단어가 나오면 이런 뜻이다" 정도로만 적습니다.

### 파인튜닝 (Fine-tuning)

이미 학습된 모델의 **가중치를 우리 데이터로 추가 조정**하는 것입니다. 프롬프트와 RAG는 가중치를 건드리지 않았는데 파인튜닝은 건드립니다. 그래서 비용과 난이도가 한 단계 다릅니다.

책 7장에서 가장 많이 참고한 것은 **파인튜닝과 RAG를 언제 고르는가**였습니다. 기준은 문제의 성격입니다.

| 문제 | 해법 |
| --- | --- |
| 모델이 **정보**를 모름 (우리 정책, 최신 데이터) | RAG |
| 모델이 **형식·말투·행동**을 못 지킴 (특정 JSON 구조, 브랜드 톤, 도메인 용어 사용법) | 파인튜닝 |
| 둘 다 | RAG 먼저, 그다음 파인튜닝 |

책의 조언은 순서입니다. 프롬프트 → RAG → 파인튜닝. 파인튜닝은 데이터가 필요하고, 모델을 바꾸면 다시 해야 하고, 학습된 지식이 시점에 고정됩니다. 대부분의 앱은 앞의 두 단계에서 끝납니다.

### PEFT와 LoRA

**파라미터 효율적 파인튜닝(Parameter-Efficient Fine-Tuning)**은 모델의 전체 가중치가 아니라 **일부만** 학습시켜 메모리와 비용을 줄이는 기법의 총칭입니다. **LoRA**가 가장 널리 쓰이는 방법으로, 원래 가중치는 얼려두고 작은 행렬 두 개만 추가로 학습합니다. 그 결과물(어댑터)이 원본 모델의 수백 분의 일 크기라서, 하나의 베이스 모델에 여러 어댑터를 갈아 끼우는 식으로 운용할 수 있습니다. 모델 허브에서 `-lora` 접미사가 붙은 파일을 보면 이것입니다.

### 양자화 (Quantization)

가중치의 **숫자 정밀도를 낮춰** 메모리를 줄이는 기법입니다. 1편에서 FP16은 파라미터당 2바이트라고 했습니다. INT8로 바꾸면 1바이트, INT4면 0.5바이트입니다. 13B 모델이 26GB에서 6.5GB로 줄어 일반 GPU나 맥북에서도 돌아갑니다. 정밀도가 낮아지니 품질이 조금 떨어지지만 생각보다 덜 떨어집니다. 오픈 웨이트 모델 파일명의 `Q4_K_M`, `int8`, `fp8` 같은 표기가 양자화 방식입니다. 로컬에서 모델을 돌려본 분이라면 이미 만난 단어일 겁니다.

### 모델 증류 (Distillation)

큰 모델(교사)의 출력으로 작은 모델(학생)을 학습시키는 것입니다. 작은 모델이 큰 모델의 행동을 흉내 내게 됩니다. 8장 데이터 합성의 한 방법으로 다뤄집니다. 모델 이름에 `distill`이 들어가면 이 방식으로 만든 것이고, 1편의 라이선스 문제에서 "출력물로 다른 모델을 학습시키지 말라"는 조항이 막으려는 것이 바로 증류입니다.

### 데이터셋 엔지니어링

8장은 파인튜닝용 데이터를 어떻게 모으고 만드는지 다룹니다. 핵심 세 축은 **품질**(틀린 예시 하나가 좋은 예시 여러 개를 상쇄), **커버리지**(실제 사용 패턴을 고르게 반영), **양**(많을수록 좋지만 품질이 우선)입니다. 직접 파인튜닝하지 않더라도 이 기준은 1편의 **평가 데이터셋**을 만들 때 그대로 적용됩니다. 평가셋도 데이터셋이기 때문입니다.

### 추론 최적화

9장은 모델을 빠르고 싸게 서빙하는 기법입니다. 배치 처리, KV 캐시 재사용, 스페큘레이티브 디코딩(작은 모델이 초안을 쓰고 큰 모델이 검증) 같은 것이고 대부분 모델 제공자의 일입니다. 우리에게 남는 것은 **성능 지표**입니다. 그 지표는 이 편 2절의 모니터링에서 다룹니다.

## 2. AI 엔지니어링 아키텍처

10장은 가장 단순한 구조에서 시작해 필요에 따라 구성 요소를 하나씩 더하는 방식으로 아키텍처를 설명합니다. 시작은 이겁니다.

```md
사용자 질의 → 모델 → 응답
```

여기서 다섯 단계를 거치며 살이 붙습니다. 책이 강조하는 것은 순서보다 **필요할 때만 더하라**는 점입니다. 처음부터 다 갖춘 구조는 디버깅만 어렵게 합니다.

### 1단계: 컨텍스트 보강

모델에게 질의만 보내는 대신 **필요한 정보를 함께 붙여** 보냅니다. 2편의 RAG와 도구가 여기 들어갑니다.

```md
사용자 질의 → [컨텍스트 구성: 검색, 도구 호출] → 모델 → 응답
```

기능이 아니라 아키텍처 관점에서 보면 이 단계는 "모델 호출 앞에 데이터 파이프라인이 붙는다"는 뜻입니다. 검색기의 지연 시간, 임베딩 비용, 문서 갱신 주기가 전부 시스템의 특성이 됩니다.

### 2단계: 가드레일 도입하기

**가드레일(guardrail)**은 시스템에 들어오고 나가는 것을 검사해 위험을 줄이는 장치입니다. 입력과 출력 양쪽에 둡니다.

**입력 가드레일**
- 개인정보(주민번호, 카드번호) 탐지와 마스킹. 외부 API로 나가기 전에 가립니다.
- 프롬프트 주입, 탈옥 패턴 탐지 (2편)
- 주제 이탈 차단. 고객 상담 봇에 코딩 질문이 들어오면 거절합니다.

**출력 가드레일**
- 형식 검증. JSON이 파싱되는가, 필수 필드가 있는가.
- 유해성, 편향 표현 검사
- 사실성 검사. 답이 검색된 문서에 근거하는가.
- 빈 응답, 거부 응답, 시스템 프롬프트 조각 유출 탐지

검사에 실패하면 어떻게 할지도 정해야 합니다. 재시도, 다른 모델로 폴백, 미리 준비한 안전한 답변, 사람 상담사로 전환.

프론트엔드 개발자가 부딪히는 문제가 하나 있습니다. **스트리밍과 출력 가드레일은 충돌합니다.** 응답을 토큰 단위로 바로 화면에 보여주고 있으면 전체 응답을 다 받은 뒤에 검사할 수 없습니다. 선택지는 세 가지입니다. 스트리밍을 포기하고 검사 후 표시하거나, 부분 응답을 청크 단위로 검사하거나, 스트리밍하되 문제가 발견되면 화면의 내용을 지우고 대체 메시지를 보여줍니다. 어느 것도 완벽하지 않고, 서비스 성격에 따라 정합니다.

### 3단계: 모델 라우터와 게이트웨이 추가

모델이 하나일 필요가 없습니다. 요청의 성격에 따라 **다른 모델이나 다른 파이프라인으로 보내는** 것이 라우팅입니다.

**모델 라우터(Router)**
간단한 잡담은 작고 싼 모델로, 복잡한 분석은 큰 모델로, 환불 문의는 환불 전용 RAG 파이프라인으로 보냅니다. 비용을 줄이고 각 요청에 맞는 처리를 할 수 있습니다.

**의도 분류기(Intent Classifier)**
라우터가 판단하는 근거를 만드는 구성 요소입니다. 사용자 질의가 어떤 **의도**인지 분류합니다. 작은 모델에 시키거나 전통적인 분류 모델을 씁니다. 라우터 자체가 느리고 비싸면 라우팅의 의미가 없으므로 **빠르고 싼 것**이 조건입니다.

```ts
import { z } from 'zod';
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod';

const Intent = z.object({
  intent: z.enum(['refund', 'shipping', 'product_question', 'chitchat', 'out_of_scope']),
});

async function classifyIntent(query: string) {
  const res = await client.messages.parse({
    model: 'claude-haiku-4-5',        // 라우팅은 빠르고 싼 모델로
    max_tokens: 64,
    system: '고객 문의의 의도를 분류합니다.',
    messages: [{ role: 'user', content: query }],
    output_config: { format: zodOutputFormat(Intent) },
  });
  return res.parsed_output?.intent ?? 'out_of_scope';
}

async function route(query: string) {
  switch (await classifyIntent(query)) {
    case 'refund':   return refundPipeline(query);      // 환불 정책 RAG + 큰 모델
    case 'shipping': return shippingPipeline(query);    // 주문 조회 도구 + 중간 모델
    case 'chitchat': return smallModelReply(query);     // 싼 모델
    default:         return outOfScopeReply();          // 모델 호출 없이 고정 응답
  }
}
```

의도 분류기는 2편의 "복잡한 작업을 하위 작업으로 나누기"가 아키텍처 구성 요소로 굳어진 형태입니다. 그리고 `out_of_scope` 경로처럼 **모델을 호출하지 않는 경로**를 만들 수 있다는 점이 비용 면에서 큽니다.

**모델 게이트웨이(Gateway)**
모든 모델 호출이 지나가는 **단일 창구**입니다. 서비스 코드가 OpenAI, Anthropic, 자체 호스팅 모델을 각각 직접 부르는 대신 게이트웨이 하나를 부르고, 게이트웨이가 실제 제공자로 연결합니다.

역할이 여러 가지 모입니다. API 키를 한곳에서 관리(서비스 코드에 키가 없음), 비용과 사용량 추적, 요청 제한(rate limiting), 제공자 장애 시 폴백, 로깅, 캐싱. 프론트엔드에서 BFF(Backend for Frontend)를 두는 이유와 거의 같습니다. 클라이언트에서 모델 API를 직접 호출하면 안 되는 이유이기도 합니다. 키가 노출되고 사용량을 통제할 수 없습니다.

### 4단계: 캐시로 지연 시간 줄이기

같은 계산을 반복하지 않는 것입니다. 책은 두 종류로 나눕니다.

**완전 일치 캐싱(Exact Caching)**
입력이 **정확히 같으면** 저장된 결과를 돌려줍니다. 입력 텍스트(또는 프롬프트 전체)를 해시해 키로 씁니다. 모델 응답뿐 아니라 임베딩 계산 결과, 검색 결과에도 적용됩니다. 특히 임베딩은 같은 텍스트면 항상 같은 벡터가 나오므로 캐시하기에 가장 안전한 대상입니다.

```ts
async function cachedEmbed(text: string) {
  const key = `emb:${hash(text)}`;
  const hit = await cache.get(key);
  if (hit) return hit;
  const vector = await embed(text);
  await cache.set(key, vector, { ttl: 60 * 60 * 24 * 30 });
  return vector;
}
```

1편의 확률적 특성이 여기서 문제가 됩니다. 모델 응답을 완전 일치 캐싱하면 "같은 질문에는 항상 같은 답"이 되는데, 이것이 원하는 동작인지 서비스마다 다릅니다. FAQ 봇이라면 좋고, 창작 도구라면 나쁩니다. 그리고 사용자별 컨텍스트가 프롬프트에 섞여 있으면 캐시 히트가 거의 안 나므로, **어느 부분을 키로 삼을지** 설계가 필요합니다.

**시맨틱 캐싱(Semantic Caching)**
입력이 정확히 같지 않아도 **의미가 비슷하면** 캐시를 재사용합니다. 1편의 임베딩과 코사인 유사도가 다시 나옵니다. 새 질의를 임베딩해서 캐시된 질의 중 유사도가 임계값(예: 0.95) 이상인 것이 있으면 그 답을 돌려줍니다. "환불 어떻게 해요"와 "환불 방법 알려주세요"가 하나의 캐시를 공유합니다.

책은 이 방식에 신중합니다. 비슷하지만 **다른 질문**에 같은 답을 돌려줄 위험이 있습니다. "3월 매출은?"과 "4월 매출은?"은 임베딩이 매우 가깝습니다. 임계값을 높이면 히트율이 떨어지고 낮추면 오답이 늘어납니다. 임베딩 호출과 벡터 검색 자체의 비용도 있어서, 실제로 히트율이 높은 서비스에서만 이득입니다.

**프롬프트 캐시**와 구분해야 합니다. Anthropic의 `cache_control`이나 다른 제공자의 프롬프트 캐싱은 **모델 제공자 쪽**에서 프롬프트의 앞부분(시스템 프롬프트, 긴 문서)에 대한 내부 연산(1편의 KV 캐시)을 재사용하는 것입니다. 응답을 재사용하는 것이 아니라 입력 처리를 재사용해 비용과 첫 토큰 시간을 줄입니다. 긴 시스템 프롬프트를 매 요청 보내는 앱이라면 이것부터 켜는 것이 가장 쉬운 최적화입니다.

### 5단계: 에이전트 패턴 추가

앞 단계까지는 흐름이 한 방향이었습니다. 질의 → 처리 → 모델 → 응답. 에이전트 패턴은 여기에 **루프**를 넣습니다. 모델의 출력이 도구 호출이면 실행하고 결과를 다시 모델에 넣습니다. 2편의 `while` 루프가 아키텍처에 들어오는 순간입니다.

책이 이것을 마지막 단계로 둔 이유가 있습니다. 루프가 생기면 **쓰기 도구**가 들어오고, 단계 수가 예측 불가능해지고, 실패 지점이 늘어납니다. 그래서 가드레일, 라우터, 로깅이 먼저 갖춰진 뒤에 붙이는 것이 순서입니다.

### 모니터링과 관찰 가능성

**모니터링(monitoring)**은 미리 정한 지표를 추적해 문제를 알아채는 것입니다. **관찰 가능성(observability)**은 시스템의 외부 출력(로그, 지표, 트레이스)만으로 내부 상태를 추론할 수 있는 성질입니다. 차이는 "미리 정의하지 않은 문제도 조사할 수 있는가"입니다. 모니터링은 "에러율이 5%를 넘었다"를 알려주고, 관찰 가능성은 "왜 넘었는지"를 파고들게 해줍니다.

**시스템 운영 지표.** 책은 DevOps의 DORA 지표를 가져옵니다.

| 지표 | 뜻 |
| --- | --- |
| **MTTD** (평균 탐지 시간) | 문제가 생긴 시점부터 알아채기까지 걸린 평균 시간 |
| **MTTR** (평균 응답 시간) | 알아챈 시점부터 해결까지 걸린 평균 시간 |
| **CFR** (변경 실패율) | 배포·변경 중 문제를 일으켜 롤백이나 수정이 필요했던 비율 |

AI 앱에서는 "변경"에 코드 배포뿐 아니라 **프롬프트 수정, 모델 버전 변경, 검색 인덱스 갱신**이 포함됩니다. 2편에서 프롬프트에 버전을 붙이라고 한 이유가 여기서 돌아옵니다. 프롬프트 변경도 배포이고, CFR에 잡혀야 합니다.

**AI 특화 지표.** 모델 출력의 품질과 성능을 봅니다.

- 형식 실패율 (JSON 파싱 실패), 거부율, 빈 응답률
- 응답 길이 분포. 갑자기 길어지거나 짧아지면 무언가 바뀐 신호입니다.
- 환각·품질 점수. 전체를 평가할 수 없으니 샘플링해서 1편의 AI 평가자로 채점합니다.
- 비용. 요청당 토큰, 사용자당 일일 비용.

**지연 시간 지표.** 프론트엔드 개발자에게 가장 직접적인 부분입니다. 자기회귀 모델은 토큰을 하나씩 만들기 때문에 지연을 세 개로 나눠 봅니다.

| 지표 | 뜻 | 사용자가 느끼는 것 |
| --- | --- | --- |
| **TTFT** (Time to First Token) | 요청부터 첫 토큰이 도착하기까지 | "반응했다"고 느끼는 시간. 스켈레톤이 사라지는 순간 |
| **TPOT** (Time per Output Token) | 첫 토큰 이후 토큰 하나당 생성 시간 | 글자가 흘러나오는 속도. 읽는 속도보다 빠르면 충분 |
| **총 지연 시간** | TTFT + TPOT × 출력 토큰 수 | 응답이 끝나기까지 |

TTFT는 입력 처리(프롬프트 길이, 검색, 가드레일)에 좌우되고 TPOT는 모델 크기와 서빙 인프라에 좌우됩니다. 그래서 대응이 다릅니다. TTFT가 길면 컨텍스트를 줄이거나 프롬프트 캐시를 켜거나 검색을 병렬화하고, TPOT가 길면 작은 모델을 쓰거나 출력을 짧게 합니다. 스트리밍은 총 지연 시간을 줄여주지 않습니다. TTFT 뒤의 대기를 **사용자가 읽는 시간으로 바꿔주는** 것입니다.

```ts
const start = performance.now();
let firstTokenAt: number | null = null;
let outputTokens = 0;

const stream = client.messages.stream({
  model: 'claude-opus-5',
  max_tokens: 1024,
  messages: [{ role: 'user', content: query }],
});

for await (const event of stream) {
  if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
    firstTokenAt ??= performance.now();
    render(event.delta.text);
  }
}

const final = await stream.finalMessage();
outputTokens = final.usage.output_tokens;

const ttft = firstTokenAt! - start;
const total = performance.now() - start;
const tpot = (total - ttft) / Math.max(outputTokens - 1, 1);
log({ ttft, tpot, total, outputTokens, promptVersion: prompt.version });
```

**로그와 트레이스.** 로그는 개별 이벤트의 기록입니다. "모델 호출, 입력 1,200토큰, 출력 340토큰, 2.1초". 트레이스는 **한 요청이 거친 모든 단계를 하나로 엮은 것**입니다. 사용자 질의 → 의도 분류(0.2초) → 검색(0.4초, 문서 5개) → 프롬프트 조립 → 모델 호출(2.1초) → 출력 가드레일(0.1초) → 응답. 어느 단계가 느린지, 잘못된 답의 원인이 검색인지 모델인지 트레이스를 보면 알 수 있습니다.

AI 앱의 로그에는 일반 앱보다 남길 것이 많습니다. 프롬프트 버전, 모델 이름과 버전, 검색된 문서 ID, 도구 호출 내역, 샘플링 파라미터. 그리고 **모델 입출력 원문**. 이건 개인정보 문제와 부딪히므로 마스킹 정책과 보존 기간을 정해야 합니다. 책이 강조하는 것은 로그가 그냥 디버깅용이 아니라 **평가 데이터의 원천**이라는 점입니다. 1편의 평가 파이프라인 3단계에서 "평가 데이터는 실제 로그에서"라고 했던 것이 여기서 연결됩니다.

### AI 파이프라인 오케스트레이션

위의 구성 요소(라우터, 검색기, 모델, 가드레일, 도구)를 **정의하고 순서대로 연결하는** 층입니다. 두 단계로 봅니다.

**구성 요소 정의.** 어떤 모델, 어떤 DB, 어떤 도구, 어떤 평가자를 쓸지 선언합니다. 각 구성 요소의 인터페이스(입력·출력 타입)를 맞춰둡니다.

**체이닝(chaining).** 구성 요소를 흐름으로 엮습니다. 순차(A → B → C), 병렬(검색과 의도 분류를 동시에), 조건 분기(의도에 따라 다른 경로), 루프(에이전트). 2편의 프롬프트 체이닝이 파이프라인 전체로 확장된 것입니다.

LangChain, LlamaIndex, Haystack 같은 오케스트레이션 프레임워크가 이 층을 추상화해 줍니다. 책의 조언은 조심스럽습니다. **처음에는 프레임워크 없이 만들어 보라.** 추상화 층이 디버깅을 어렵게 하고, 프레임워크의 기본 프롬프트가 우리 의도와 다를 수 있고, 프레임워크가 지원하지 않는 기능이 필요해질 때 벗어나기 어렵습니다. 파이프라인이 안정되고 반복 패턴이 보이면 그때 도입을 검토합니다.

프론트엔드 개발자 눈에는 이 층이 그렇게 낯설지 않습니다. 결국 `async` 함수들을 조합하는 일입니다.

```ts
async function handle(query: string, userId: string) {
  const trace = startTrace({ query, userId });

  const [intent, history] = await Promise.all([         // 병렬
    trace.span('classify', () => classifyIntent(query)),
    trace.span('history', () => loadHistory(userId)),
  ]);

  if (intent === 'out_of_scope') return trace.end(outOfScopeReply());   // 조건 분기

  const docs = await trace.span('retrieve', () => retrieve(query, intent));   // 순차
  const answer = await trace.span('generate', () => generate({ query, docs, history }));
  const checked = await trace.span('guard', () => outputGuardrail(answer, docs));

  return trace.end(checked);
}
```

프레임워크가 하는 일도 본질은 이것입니다. 다만 각 `span`이 기록하는 것이 평가와 디버깅의 재료가 된다는 점을 처음부터 염두에 두는 것이 다릅니다.

## 3. 사용자 피드백

10장의 후반부입니다. 책이 이 절을 아키텍처 뒤에 붙인 이유는 명확합니다. 1편에서 본 AI 엔지니어링의 순서, **제품 → 데이터 → 모델**에서 "데이터"가 바로 사용자 피드백입니다. 평가셋을 만들고, 프롬프트를 개선하고, 언젠가 파인튜닝할 데이터가 여기서 나옵니다.

### 대화형 피드백 추출

대화형 인터페이스의 특징은 **피드백이 대화 안에 이미 들어 있다**는 점입니다. 사용자는 별점을 누르지 않아도 다음 메시지로 평가를 남깁니다.

- **부정 신호**: "아니 그게 아니라", "다시", "내가 물은 건", 같은 질문 반복, 오류 지적("그 함수는 없는데")
- **긍정 신호**: "고마워", "됐다", 다음 단계로 진행, 제안된 내용을 그대로 사용

이 신호를 자동으로 뽑아내는 것도 모델의 일입니다. 대화 로그를 작은 모델에 넣어 "이 턴에서 사용자가 불만족을 표현했는가"를 분류하면 명시적 피드백보다 훨씬 많은 데이터가 나옵니다. 정확도는 떨어지지만 양이 이를 보상합니다.

### 명시적 피드백과 암시적 피드백

**명시적 피드백(explicit feedback)**은 사용자가 **의도적으로** 남기는 평가입니다. 좋아요/싫어요, 별점, 두 답변 중 선택(A/B 비교), 자유 텍스트 의견. 해석이 쉽고 정확하지만 **양이 적습니다.** 대부분의 사용자는 버튼을 누르지 않습니다. 누르는 사람은 아주 만족했거나 아주 불만인 사람이라 분포가 양극화됩니다.

**암시적 피드백(implicit feedback)**은 사용자의 **행동에서 추론**하는 평가입니다.

| 행동 | 해석 |
| --- | --- |
| 응답을 복사함 | 유용했을 가능성 |
| 다시 생성(regenerate) 버튼 | 불만족 |
| 응답을 편집해서 사용 | 방향은 맞지만 부족. 편집 내용 자체가 정답 데이터 |
| 스트리밍 중 중단 | 초반부터 틀렸거나 너무 김 |
| 대화를 이어감 / 바로 떠남 | 맥락에 따라 다름 |
| AI 제안 코드의 수락률, 수정 없이 남은 비율 | 코딩 도구의 핵심 지표 |

양이 많고 자연스럽지만 **해석이 애매합니다.** 대화가 길어진 것이 만족(계속 쓴다)인지 불만(계속 고쳐 달라고 한다)인지는 맥락을 봐야 합니다.

두 가지를 함께 쓰는 것이 답입니다. 암시적 신호로 넓게 잡고, 명시적 피드백으로 검증합니다.

### 피드백 설계

피드백을 **언제, 어떻게** 요청할지는 UI 설계 문제입니다. 프론트엔드 개발자의 일입니다.

**언제.**
- 온보딩 시점: 취향, 목적, 사용 언어 같은 초기 정보. 이후 응답의 기준이 됩니다.
- 응답 직후: 가장 흔한 좋아요/싫어요. 마찰이 없어야 합니다.
- 문제가 감지된 시점: 재생성 버튼을 눌렀을 때 "무엇이 아쉬웠나요?"를 짧게 묻습니다. 사용자가 이미 불만을 표현한 순간이라 응답률이 높습니다.
- 사용자가 자발적으로 대화 안에서 말할 때: 위의 대화형 피드백.

**어떻게.**
- 마찰을 최소화합니다. 필수로 만들지 않고, 클릭 하나로 끝나게 합니다.
- 비교 방식이 유용합니다. 두 응답을 나란히 보여주고 고르게 하면 절대 점수보다 신뢰할 수 있는 데이터가 나옵니다(1편의 비교 평가). 단, 사용자가 두 개를 읽어야 하는 부담이 있으므로 일부 요청에만 씁니다.
- 피드백이 **반영된다는 것을 보여줍니다.** "이 피드백은 답변 개선에 사용됩니다" 같은 안내가 응답률을 올립니다.
- 편집을 피드백으로 씁니다. 사용자가 AI 초안을 고쳐서 보냈다면 (초안, 수정본) 쌍이 가장 질 좋은 학습 데이터입니다. 편집 가능한 UI를 만드는 것 자체가 피드백 수집 설계입니다.

### 피드백의 한계

책은 피드백을 그대로 믿으면 안 되는 이유도 적습니다.

**편향.** 피드백을 남기는 사람이 전체 사용자를 대표하지 않습니다. 불만인 사람이 더 많이 남기고(부정 편향), 비교 UI에서는 먼저 보인 답을 고르는 경향이 있고(위치 편향), 사용자는 자신에게 동의하는 답을 좋아합니다(아첨을 강화할 위험).

**조작.** 악의적인 사용자가 잘못된 피드백을 대량으로 남겨 모델이나 순위를 왜곡할 수 있습니다. 피드백을 학습에 쓸수록 이 위험이 커집니다.

**피드백 루프(degenerate feedback loop).** 피드백으로 개선한 모델이 특정 유형의 답을 더 자주 내고, 그 답이 더 많은 피드백을 받고, 다시 강화되는 순환입니다. 추천 시스템의 "인기 있는 것이 더 인기 있어지는" 문제와 같습니다. 피드백을 반영할 때는 그것이 다양성을 줄이고 있지 않은지 따로 봐야 합니다.

프론트엔드 개발자로서 배운 것은 이겁니다. 피드백 UI는 "붙이면 좋은 것"이 아니라 **데이터 파이프라인의 입구**입니다. 어떤 버튼을 어디에 두는지가 나중에 어떤 평가셋이 만들어지는지를 결정합니다.

## 시리즈를 마치며

세 편에 걸쳐 책을 읽으며 메모한 키워드를 하나씩 다시 조사하고 제 말로 적었습니다. 시작할 때의 질문은 "프론트엔드 개발자인 내가 AI 엔지니어라고 할 수 있는가"였습니다. 책의 정의로는 그렇습니다. 파운데이션 모델을 가져다 제품을 만드는 사람이 AI 엔지니어이고, 저는 그 일을 하고 있습니다.

다만 이름을 붙이는 것과 그 이름에 맞는 사람이 되는 것은 다른 일입니다. 용어를 정리하면서 제가 만든 AI 기능을 돌아봤습니다. 검색 방식을 설명하지 못하는 RAG, 버전 관리가 안 된 프롬프트, 좋아요 버튼만 있고 아무 데도 연결되지 않은 피드백. 단어의 뜻을 모른 채로도 동작하는 것은 만들 수 있었지만, 왜 동작하는지와 왜 가끔 안 되는지는 설명하지 못했습니다.

이 시리즈에서 프론트엔드 개발자의 영역이라고 느낀 것을 다시 적으면 이렇습니다.

- **스트리밍 UX와 지연 시간 지표.** TTFT와 TPOT를 측정하고 사용자가 기다리는 방식을 설계하는 일.
- **구조화된 출력과 형식 검증.** 모델 출력을 화면에 안전하게 뿌리는 일.
- **컨텍스트와 메모리 관리.** 화면의 대화와 모델에 보내는 컨텍스트를 분리해 설계하는 일.
- **피드백 UI.** 평가 데이터의 입구를 만드는 일.
- **입력 처리.** 모델이 읽는 모든 텍스트를 사용자 입력과 같은 등급으로 다루는 일.

전부 원래 하던 일의 연장입니다. 새로운 것은 그 뒤에 확률적으로 동작하는 구성 요소가 하나 들어왔다는 점이고, 그 구성 요소를 이해하는 데 필요한 단어가 이 세 편입니다.

책을 덮고 나서 가장 오래 남은 문장은 1편에 적었던 것입니다. 평가할 수 없는 것은 개선할 수 없다. 다음에 AI 기능을 만들 때는 프롬프트보다 평가셋을 먼저 만들어 보려고 합니다. 그게 되면 다시 글로 남기겠습니다.
