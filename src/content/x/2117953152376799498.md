  "text": "We need to reconsider our priors on code readability.\n\nHumans, compared to agents, are pretty slow at understanding large quantities of text. So in the old days, readability was important so the human could efficiently grok what was going on.\n\nSo readability now comes down to:\n\n1. Can a human, if needed, jump in and understand the code\n2. Does the code use the same domain language as the human describing the code?\n\n1 helps with observability and the occasional spot checks you need to do on important PR's. 2 helps the agent translate the words you use into code changes.\n\nIn other words, readability is now a nicety, not a necessity.\n\nThe way agents 'read' code is different - good agents are all about gathering data about how the code works. They'll prod around with it, execute parts of it.\n\nSo 'readability' to agents really means 'verifiability'. How easy it is to mess about with that code to see it working.\n\nLet's take this scenario:\n\n- You have a huge module in your codebase that uses all sorts of complex performance tricks\n- It has 100% test coverage\n\nA talented human would need an hour or two to get comfortable working in that module.\n\nAn agent needs zero time. They verify it with the tests, poke about a bit, and they're good to go.\n\nThe takeaways:\n\n- When judging a module (or a codebase), don't think about how easy the code is to read\n- Instead, think about how easy it is to verify\n- Design your codebase so modules can be tested and verified independently\n- Feel free to sacrifice a bit of readability for performance\n- Cyclomatic complexity and function size don't matter to agents",
