  "text": "The code review is no longer a process problem, to me it more closely resembles a data problem.\n\nSo our approach to how we treat, build for and reason about it also needs to change.\n\nCode review is now a data problem\n\nMaybe it's time I start sharing more about something I've been iterating and building for almost a year now.\n\nWhen I've started working on building agents for QA, it did not take too much time for me to realize that, althought a great low-hanging fruit, QA is not the main friction point for teams. The main issue that all teams since earlier this year started to feel was code reviews.\n\nAnd for any company out there there's a strategy, or coping mechanisms, to deal with this issue. Sometimes it involves throwing agents at it to bring you digests, sometimes there's a triaging process and many other forms of \"there's an agent for that\".\n\nAlthough I don't necessarily disagree with such approaches, for me it misses some marks:\n\n1.  Validation is not a natural part of the process, as in it gets lost or does not have a natural surface area\n\n2. Understanding the changes is often not an easy task\n\n3. The PR itself is often not the right unit of change to triage and base automations on\n\nThe reason for all of that is very well described by @addyosmani here. The PR itself is not the right primitive anymore. Code is not a knowledge issue, now it is a data driven problem.\n\nBut even on the final work I believe there's room for deconstruction.\n\nNot all code has the same importance\n\nSo treating the whole branch as a unit of change is no longer the right way to handle it. It's a mix of a tokenomics issue, validation and also correctness issue.\n\nDifferent parts of the codebase can have different importance, based on blast-radius, historical context (outages, hot-paths, etc), complexity curves or structural importance. All of which are different dymensions to consider when assessing between automation (CI), agentic or human reviews to be necessary.\n\nWe are all bankrupt, cognitively\n\nOne of the reasons that reviewer bots are so good is because we want them to take away the burden of responsibility on a codebase that we no longer understand. But they miss the fact that we are still responsible for them and still should understand them. No on a line-by-line basis but on a higher level, a system of changes.\n\nOur products cannot thrive without our careful curation.\n\nSo the next thing to surplant code reviews as we knew it is no longer on assessing the code, but verifying the changes.\n\nSo the solution to this data problem is, as any data problem before it, to use the right visualization tools.\n\nChange and context\n\nWe are now in need of a system that attributes change to context. This is not just for us but for agents too. Though models have become very capable of sourcing their needs to perform a task, often they can be blindside or in worst cases get lost in the larger goal or scope.\n\nWe are now tempted to 'code is throwaway' mentality, but I feel like that is still wasteful. Agents should be able to use their inteligence alongside the right set of tools to help them independently source and review scope for changes.\n\nThis is only the beginning, I'm planning to start colecting early feedback on this as early as next week as I proceed with my last 'hill climbs' before this thing is ready for external attention. But I'm now also curious to hear from different people their struggles and friction points and sticking points when using code reviewing tools out there.\n\nhttps://x.com/i/article/2017338533850042368",
